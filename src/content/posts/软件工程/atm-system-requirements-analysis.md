| 四、实验过程（实验步骤、记录、数据、分析） 1.所选题目：ATM系统  2.系统需求陈述 某银行拟开发一个自动取款机系统，它是一个由自动取款机、中央计算机、分行计算机及柜员终端组成的网络系统。ATM和中央计算机由总行投资购买。总行拥有多台ATM，分别设在全市各主要街道上。分行负责提供分行计算机和柜员终端。柜员终端设在分行营业厅及分行下属的各个储蓄所内。该系统的软件开发成本由各个分行分摊。 银行柜员使用柜员终端处理储户提交的储蓄事务。储户可以用现金或支票向自己拥有的某个账户内存款或开新账户。储户也可从自己的账户中取款。通常一个储户可以拥有多个账户。柜员负责把储户提交的存款或取款事务输进柜员终端，接收储户交来的现金或者支票，或付给储户现金。柜员终端与相应的分行计算机通信，分行计算机具体处理针对某个账户的事务并且维护账户。 所谓现金兑换卡就是一张特制的磁卡，上面有分行代码和卡号。分行代码唯一标识总行下属的一个分行，卡号确定了这张卡可以访问哪些账户。通常，一张卡可访问储户的若干账户，但是不一定能够访问这个储户的全部账户。每张现金兑换卡仅属于一个储户所有，但是，同一张卡可能有多个副本，因此，必须考虑同时在若干台ATM上使用同样的现金兑换卡的可能性。也就是说，系统应该能够处理并发的访问。 当用户把现金兑换卡插入ATM之后，ATM就与用户交互，以获取有关这次事务的信息，并与中央计算机交互关于事务的信息。首先，ATM要求用户输入密码，接下来ATM把这张卡上读到的信息以及用户输入的密码传给中央计算机，请求中央计算机处理这些信息并处理这次事务。中央计算机根据卡上的分行代码确定这次事务与分行的对应关系，并且委托相应的分行计算机验证用户密码。如果用户输入的密码是正确的，ATM就要求用户选择事务类型(取款，查询等)。当用户选择取款时，ATM请求用户输入取款额。最后，ATM从现金出口吐出现金，并且打印账单交给用户。 3.系统需求分析 ATM系统需求说明书 3.1 获取用户需求   3.1.1 业务需求 银行计划构建一个覆盖全市的自动取款机（ATM）系统，系统由以下部分组成： ATM 终端：部署在街道、小区、商场。用于储户自助办理查询/取款业务。 中央服务器（CentralServer）：总行部署，负责 PIN 验证、事务路由、协调分行服务器处理请求。 分行服务器（BranchServer）：每个分行负责管理本行账户余额、事务执行、交易日志写入。 柜员终端（Teller GUI）：分行柜员使用，用于开户、存取款、支票、卡片管理等。 MySQL 数据中心：存储客户、账户、卡片、柜员、交易日志、审计日志等核心数据。 必须满足： 支持 并发访问（同一张卡可能被同时使用多个副本）。 所有关键操作必须记录 审计日志（由 admin 可查看）。 ATM 取款必须经 CentralServer → BranchServer → MySQL 完整链路处理。 卡片 PIN 不能以明文存储。 不同角色拥有不同权限（admin / manager / clerk）。  3.1.2 用户需求 1）ATM 用户（Customer） 插卡 → 输入 PIN → 选择账户 查询余额 取款 获取交易凭条 2）柜员（Clerk） 创建客户 创建账户 存款 取款 支票存款 查看交易记录 3）分行经理（Manager） 除柜员功能外，还需要： 创建银行卡 卡绑定账户 4）系统管理员（Admin） 除 manager 功能外，还需要： 创建柜员（admin/manager/clerk） 查看审计日志 管理系统权限 5）系统维护人员 管理数据库 监控服务器运行状态  3.1.3 功能需求 系统分四大功能模块：  （1）ATM 功能  （2）柜员终端功能（含权限）  （3）中央服务器功能 PIN 验证 分行路由 ATM 请求转发 事务协调 返回 ATM 结果  （4）分行服务器功能 查询余额 修改余额 落库交易记录 支票处理  3.1.4 性能需求   ATM 查询操作平均响应时间：≤ 1 秒   取款操作平均响应时间：≤ 2 秒   支持 100+ 并发 ATM 用户   数据库操作符合 ACID   日志写入可靠，可追溯  3.1.5 其它需求   安全性：PIN 必须使用 SHA256 哈希   稳定性：数据库异常时必须能够回滚   可维护性：使用模块化架构   可扩展性：可以扩展到多城市、多分行   审计性：所有敏感操作必须记录审计日志  3.2 建立对象模型  3.2.1 确定类 根据代码模块 dao.py / CentralServer / BranchServer，我们得到以下类： 实体类： Customer | 实验结论与体会 1. 需求分析阶段在软件开发中处于什么样的位置？ 需求分析阶段是整个软件开发生命周期的 起点 和 基础核心阶段，其位置可以概括为： （1）软件开发流程的前置关键阶段 需求分析在软件立项之后、系统设计之前进行，是整个系统开发的逻辑起点。 它决定系统需要“做什么”(What)，而不是“怎么做”(How)。 （2）所有后续活动的依据 需求分析直接影响： 系统设计（架构、模块划分） 程序实现（代码编写） 系统测试（用例依据） 用户文档（功能说明） 项目验收（是否满足需求） 如果需求分析不准确，后续所有工作都会在错误方向上推进，最终系统即使做得再精良也无法满足用户需求。 （3）需求分析是成本最低、收益最大的阶段 越早发现问题，纠错成本越低；到了编码或测试阶段再发现需求错误，修复成本会呈指数级增加。 因此，需求分析阶段在软件开发中处于： 最前端、最基础、最关键的位置，是整个项目的蓝图与核心依据。  2. 如何理解“在软件工程中，所有风险承担者都关注需求分析阶段”这段话？ 这段话的核心意思是： 需求分析不仅影响开发人员，而是影响整个项目所有角色。所有与项目成功相关的人，都必须关注需求是否被正确获取和表达。 这是因为：  （1）每个风险承担者都有利益相关 客户 / 用户 希望软件真正解决他们的问题 若需求不清晰，最终产品可能无法使用 会直接承受项目失败或返工带来的损失 业务/需求分析员 负责挖掘和表达需求 若需求文档错误，他就是直接责任人 开发人员 需求是代码编写的基础 需求错误 → 代码方向错误 → 大量返工 测试人员 测试用例来自需求文档 若需求模糊，无法判断“什么是正确的行为” 用户文档编写者 需要基于需求说明描述系统功能 项目管理者 需求变更会直接影响项目进度、成本、质量 风险最高的部分往往来自需求不稳定 客户管理者（产品经理等） 需求错误代表产品决策失败，影响业务和信誉  （2）需求是所有风险的“单点入口” 需求阶段若出现问题： 整体方向错误 功能不满足用户 测试无法验收 文档、自助服务体系不成立 工期严重延误 成本爆炸 项目失败的风险极高 因此大家都特别关注需求分析，因为： 如果需求不清晰、不完整或不正确，那么整个软件工程的风险都将成倍放大。  （3）需求分析阶段是所有角色共同的“风险控制点” 每个相关角色都必须参与，包括： 用户提出需求 需求分析员深化需求 管理层审核业务目标 开发、测试参与需求评审 确保所有人对需求有一致理解 因此需求分析不是某一群人的工作，而是： 整个团队共同关注、共同确认、共同承担风险的过程。  总结一句话： 需求分析阶段的重要性之所以高，是因为： 它决定项目要做什么，而所有参与者都要围绕这个“要做什么”开展工作，因此每个风险承担者都必须高度关注需求是否正确。       2025年  11  月  25  日 |
